## 1. 工程概览

本工程整合了官方三个例程的功能：

- `lab_ex1_mipi_hdmi`：MIPI 采集 + HDMI 实时显示
- `lab_ex2_edge`：ISP 链路中的边缘检测
- `lab_ex3_osd`：HDMI 输出前的 OSD 叠加

整合版额外提供：

- KEY1 实时切换 RAW / EDGE 算法
- KEY2 / KEY3 调节摄像头曝光
- OSD 显示安路 Logo、动态文字、帧计数和当前算法状态
- 115200-8-N-1 UART 调试日志
- 边缘检测改为全分辨率梯度 + luma 灰度公式 + √ 曲线查表输出灰度（见第 4 节），已上板验证
- 输出分辨率升级到 1280x720@60（见第 10 节），各级参数已同步，已上板确认

## 2. 系统数据流

```text
MIPI 摄像头
  -> MIPI D-PHY RX
  -> CSI / RAW10 解包
  -> ISP（demosaic -> AWB）
  -> 边缘检测（edge_detect_96）
  -> RAW / EDGE 算法选择 MUX
  -> DDR2 帧缓存
  -> HDMI 时序
  -> hdmi_mixer（Logo + 动态文字 + 帧计数 + 算法状态）
  -> hdmi_tx
  -> 显示器
```

RAW 路径和 EDGE 路径并行工作，MUX 在按键切换后选择其中一路送入 DDR。

## 3. 按键定义

| 板载按键 | 顶层信号 | 引脚 | 功能 |
|----------|----------|------|------|
| KEY1 | `I_button[1]` | D5 | RAW / EDGE 算法切换 |
| KEY2 | `I_button[0]` | A9 | 曝光目标值递减 |
| KEY3 | `I_button[2]` | B9 | 曝光目标值递增 |

KEY1 采用约 20 ms 消抖，短按一次切换一次算法。KEY2、KEY3 当前为短按调节，
不支持长按连续调整。KEY4 暂未使用。

## 4. 边缘检测实现

`user_source/hdl_source/isp/edge_detect_96.v` 相对官方实现有四处结构改动（前两处
来自 `feat/edge-magnitude`，第三处 `feat/edge-luma`，第四处 `feat/edge-lut`）。输入输出仍是
96 位 × 4 像素/拍，`O_tuser` / `O_tlast` / `O_tvalid` 与数据严格对齐，但本版总
延迟为 2 拍，且输出的 4 个像素对应列 4k-1..4k+2，因此整幅边缘图相对 RAW
**左移 1 像素**。

1. **全分辨率梯度**。官方实现先做 `grp_gray = (gray0+gray1+gray2+gray3)>>2`，
   把同拍 4 个像素平均成一个再做 Sobel，真正参与梯度运算的是宽度只有 1/4 的图
   （1024x600 下是 256×600，现在 720P 下是 320×720），
   结果再复制回 4 个像素。宽度小于 4 像素的竖线因此被 4 倍组平均压到阈值以下
   而完全消失。本版为每个像素单独算 Sobel（4 路并行）。
2. **输出梯度灰度而不是硬二值化**。`I_thresh` 只作噪声门限：低于门限输出 0（压掉
   噪声），高于门限按下面的显示曲线出灰度，而不是硬切二值。同时删掉了三点多数滤波，
   它会把细笔画产生的孤立边缘像素直接抹掉。
3. **灰度公式换成官方 720P 例程的 `R/4 + G/2 + B/4`**（最大 253，不回绕、不用除法）。
   旧公式 `(R+G+B)/3` 的加法在 8 位表达式里先回绕，把全图**绝对亮度**压到 0..85
   （R=G=B=128 只剩 42、255 只剩 84）。
   **但它并不压缩局部对比度**：旧公式是斜率恒为 1 的锯齿，段内相邻像素的差分原样
   保留（实测 Δ=8 时 232/248 个相邻位置保留），只在每 85 级跨段时冒出 ±85 的假跳变
   ——那会在平滑表面上产生成片假边缘（白块/弧线）。所以换公式的实际收益是
   “去掉回绕假边 + 绝对亮度正确 + 少一个除法”，**不能**据此把门限或增益按 3 倍去
   换算。这一点踩过坑：一度把 TH 放大到 48，上板后弱边缘整片消失、只剩强轮廓。
4. **显示映射改成 √ 曲线查表**（`edge_curve`，白点 K=256）。干净阶跃边缘的
   `|gx|+|gy| ≈ 4Δ`，而线性映射经显示器 gamma（≈2.2）折算后感知响应是 Δ^2.2 ——
   弱边缘（Δ≈8）只剩约 1% 白场亮度、基本看不见，强边缘又直接过曝。换成
   `code = clamp(round(255·√(mag/K)), 255)` 后感知响应约为 `(mag/K)^1.1`：
   Δ=8 从 1% 提到 10.2%，Δ≥64 仍映射为纯白。表由 `tools/gen_edge_lut.ps1` 生成
   （`-WhitePoint 128` 更亮、Δ≥32 即过曝；`512` 更保守、画面偏灰）。查表只额外花
   约 80 个 LUT，时序余量反而比线性版好（+9 ps → +569 ps）。

幅度对比（下表是 **1024x600 + 旧灰度公式** 下的历史数据，用来比较“组平均 vs 全
分辨率”的几何差异，不代表当前配置的数值）：

| 竖线宽度 | 官方组平均版 | 原 `EDGE_TH=132` | 全分辨率版（门限 16） |
|----------|--------------|------------------|------------------------|
| 1 像素   | 40           | 消失             | 168                    |
| 2 像素   | 84           | 消失             | 252                    |
| ≥3 像素  | ≥124         | 3 像素仍消失     | ≥252                   |

上表是 Sobel 幅度本身（旧公式的压缩域）。两版的局部差分基本一致，所以新公式下
这些幅度也差不多；旧公式多出来的 ±85 假跳变会让部分区域直接饱和成白块，这正是
旧版图里那些成片白色细节的来源。

上板 A/B 对比（第一步：组平均 + 增益 2 / 第二步：全分辨率 + 增益 0）的结论：
**第一步的笔画更粗，但两版明暗肉眼分辨不出**。粗笔画说明第一步那种"更好看"
有相当一部分来自组平均把边缘摊成 4 像素的副作用；明暗无差异说明真实笔画宽度多在
3 像素以上、两版都已接近饱和。因此保留全分辨率几何，把增益调回 1。

上板演进：旧公式 + 门限 16 + 线性 ×2（1024x600 与 720P 都测过，细笔画良好）→
luma 公式 + 门限 16 + 线性 ×1（**旧版那种回绕白块消失、观感更好**）→
luma 公式 + 门限 16 + √ 查表 K=256（**细节明显更丰富，但刚过门限的噪点也变多**）→
当前把门限提到 **24** 来压噪（Δ≥6 才可见），bitstream 在
`tmp/720p_edge_ab/edge_sqrt_k256_th24.bit`，**待上板确认细节损失是否可接受**。
TD 结果：门限 16 版 +569 ps、门限 24 版 +686 ps（都是 Hold +20 ps、0 违例）。

减噪就动门限：`EDGE_TH` 24~32 等价于只放行 Δ≥6~8 的像素，砍掉的主要是噪声和最弱的
纹理；不要靠调大白点 K 来"压暗"——那是把包括有用弱边缘在内的所有东西一起压暗。

行缓存改成**三块按行轮转的 block RAM**：每块 320×48 位（1024x600 时是 256×48，
行缓存按 `IMG_WIDTH/4` 自动跟着分辨率走），保存一行内 6 个平滑灰度
（对应列 4k-2..4k+3），每周期只写其中一块、只读另外两块，读写永不同址且读地址已
寄存。这是必需的——全分辨率下若沿用官方那种异步读写法，行缓存会落成触发器，直接
把器件 FF 资源耗尽（TD 报 `PHY-9002 Placer initialization failed`）。改成 BRAM
后最终时序反而由负转正。

官方实现保留的已知限制：

- （旧实现遗留，本版已修）灰度计算 `R+G+B` 在 8 位表达式里回绕后再除以 3，会产生
  约 85 为周期的锯齿并把全图亮度压到 0..85（上表幅度偏小即由此而来）；
- `data96_128` 的 128 位打包计数器不会被帧起始单独复位。

任何进一步的数值“修正”都必须保持 `O_tuser` / `O_tlast` 与数据对齐，
并用固定文字目标做整幅边缘图对比后再替换，不能只比较“是否能检测到边缘”。

## 5. OSD 与画面状态

`hdmi_mixer.v` 负责在 HDMI 数据输出前叠加：

- 左上角：安路 Logo；
- 中部：动态文字和帧计数；
- 右上角：当前算法状态 `RAW` / `EDGE`。

算法状态文字位置由 `STATUS_OSD_X`、`STATUS_OSD_Y` 参数控制。切换算法瞬间
可能出现短暂的一帧撕裂，下一帧恢复属于当前设计的预期现象。

720P 下这几处坐标也调过：动态文字/帧计数 `DYN_OSD_X = 540`（1280 宽下水平居中），
右上角的 RAW/EDGE 状态字 `STATUS_OSD_X = 1100`，Logo 仍在左上角 160x160。

Logo 的 ROM 地址原来是 `S_logo_y * LOGO_W`，会被综合成一个 DSP 乘法器，而
`mult0 → Logo ROM → O_hdmi_data_reg` 正好是 75MHz 像素域上最紧的一条路径（TD 报
Setup 差 99 ps 就落在它上面）。`LOGO_W = 160 = 128 + 32`，现在写成移位加法
`((y<<7) + (y<<5)) + x`，数值完全等价、少用一个 DSP，这条路径也不再是瓶颈。

## 7. 串口运行时日志

开发板 Type-C USB 带有 USB 转 UART，FPGA TXD 使用 H1 引脚。日志格式为
115200-8-N-1，每秒输出一行：

```text
DBG:F=xxxx A=xxxx G=xxxx T=xxxxxx N=xxxxx B=xxxxx C=xxxxx M=xxx L=xx
```

字段含义：

- `F`：HDMI 显示帧计数
- `A`：AE 曝光目标值
- `G`：AG 增益目标值
- `T`：24 位流水线状态位图，定义见 `debug_uart_logger.v` 顶部注释
- `N`：当前帧非零像素计数
- `B`：亮度不低于 64 的像素计数
- `C`：亮度不低于 128 的像素计数
- `M`：RAW10 最大值
- `L`：显示层最大值

EDGE 模式下显示层是梯度灰度，所以 `N` / `B` / `C` 实际是 mag ≥ 16 / ≥ 32 / ≥ 64
的像素计数，可直接用来选边缘门限，不必只靠肉眼看画面。

读取日志：

```powershell
.\tools\read_debug_uart.ps1 -Port COM3
```

脚本会同时打印到终端并追加写入 `debug_uart.log`。

## 9. 当前已知风险

- 边缘实现已改为全分辨率梯度 + 灰度输出，画面与官方例程不同；1024x600 与 720P
  都已上板确认细笔画效果良好、画面无异常（无 4 像素梳状纹理、无水平错位），但
  **尚未做与固定文字目标的整幅边缘图数值对比**，边缘质量目前仍是主观确认；
- 720P 是本工程第一次跑的模式：摄像头寄存器表取自官方 `lab_ex*_SC500_720P` 例程，
  已上板实测合格。以后若改 sensor 窗口/帧率、PLL 或 HDMI 时序，必须按第 10 节的
  对照表整链一起改，并重新综合与上板确认；
- 边缘图相对 RAW 左移 1 像素、总延迟 2 拍，这是设计选择而非缺陷；
- 官方和整合版都没有完整的 ready/backpressure 闭环，DDR 或 FIFO 拥塞时
  需要重点检查数据是否被丢弃；720P 的 DDR 读写量比 1024x600 高 50%（写+读约
  330 MB/s），上板实测画面稳定，但长时间运行或加大算法负载时仍要用 `DBG:` 日志
  的帧计数和 N/B/C 复查有没有丢帧；
- 时序余量一直很薄：720P 上出现过 Setup **-99 ps**（只差一个端点）的版本。而且
   TD 的布局布线是确定性的——同一份网表重跑，HPWL、拥塞和时序数字完全一样，
  不能指望“再跑一次就好了”，只能改逻辑或改约束。去掉 `hdmi_mixer` 里那个 DSP
  乘法器后，TH48 那版是 Setup +728 ps；当前 TH16 版布线落点不同、只有 +9 ps
  （仍 0 违例）。余量对布局落点很敏感，继续加功能后必须重新确认；
- √ 曲线把显示映射的低端一起提亮了：上板确认**细节明显更丰富，但刚过门限的噪点
  也变多**。这是曲线形状的固有代价（不是 bug）——减噪靠提 `EDGE_TH`（24~32 等价于
  只放行 Δ≥6~8），而不是把白点 K 调大（那会把有用的弱边缘一起压暗）。当前
  `EDGE_TH=24` 就是压噪试验，**细节损失是否可接受还没上板确认**；
- 白点 K 是"多强算纯白"的旋钮，改动只需用 `tools/gen_edge_lut.ps1 -WhitePoint <值>`
  重新生成表；K 越小整幅越亮、也越容易过曝和显噪（K=128 白点 Δ≈32，K=512 更保守）。
  两个旋钮分工：`EDGE_TH` 管"多弱才出现"（噪声地板），K 管"出了灰度怎么映射"；
- 调 TH / 增益时**不要按灰度公式换算**：公式改的是绝对亮度，Sobel 只看局部差分，
  两者不是一回事——TH 48 那一版就是这么踩的坑，弱边缘被整片拦掉。

## 10. 分辨率与时钟配置（720P）

2026-09 起整条链路从 1024x600 升到 **1280x720@60，75 MHz 像素时钟**。分辨率是
整链参数，不能只改一处；改动时对照下表一起改，改完必须重新综合与布局布线。

| 环节 | 现在（720P） | 之前的 1024x600 |
|------|--------------|-----------------|
| 摄像头窗口 | 1280x720，起点 (512,512)，HTS 1600 / VTS 1000，VBIN+HSUB，2-lane 约 480 Mbps | 1024x600，起点 (1024,1024)，HTS 2852 / VTS 1127 |
| 摄像头寄存器表 | `uics500reg.v`（模块名不变，内容取自官方 `lab_ex*_SC500_720P` 例程） | 旧表 |
| PLL | C4 75 MHz（像素）/ C5 375 MHz（TMDS serial）/ C1 23.81 MHz（摄像头 MCLK 与 I2C） | C4 52 / C5 260 / C1 24.07 MHz |
| VTC | 1280x720，帧 1650x750，sync 1390/1430、725/730 | 1024x600，帧 1344x635 |
| HDMI TX core | HTOTAL 1650 / HSA 40 / HFP 110 / HBP 220 / VTOTAL 750 / VSA 5 / VFP 5 / VBP 20 | 1344 / 24 / 160 / 136、635 / 2 / 12 / 21 |
| ISP、边缘、裁剪、uial2axis、hdmi_mixer | 全部 1280x720 | 1024x600 |
| MIPI 输入约束 | `mipi_rx_ck_pad` period 4.167ns（480 Mbps/lane，CSI 域实测 59 MHz） | period 2.222ns（过度约束） |
| 串口日志 | `CLK_HZ = 75000000` | 52000000 |

摄像头寄存器表的顺序也要留意：出厂文件要求先写 `0x0100=01`（stream on，索引 114），
等 10 ms 再写 `0x302d=00`（索引 115），这个延时由 `uicfgcs500.v` 里的
`POST_STREAM_DELAY` 实现，换表时不要丢掉。

构建结果（TD Release_2026.1_SP2，`feat/edge-lut`，luma 公式 + TH16 + √ 查表 K=256）：
**final Setup WNS +569 ps / TNS 0 / 0 违例，Hold WNS +20 ps / 0 违例**，slices 16425
（77.42%），ERAM 39，DSP 8（查表比线性版多约 80 个 LUT、slices +333，相比 +9 ps 的
线性版余量反而更好）。bitstream：
`td_project/camera_to_dsi_display_Runs/phy_1/camera_to_dsi_display.bit`。

**已上板确认**：1280x720 画面正常、RAW/EDGE 切换与曝光按键可用、OSD 位置合适，
720P 改造到此完成。后续再调算法参数时，用 `tools/read_debug_uart.ps1` 读 `DBG:`
日志（帧计数、N/B/C）做客观对比。
