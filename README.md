## 1. 工程概览

本工程整合了官方三个例程的功能：

- `lab_ex1_mipi_hdmi`：MIPI 采集 + HDMI 实时显示
- `lab_ex2_edge`：ISP 链路中的边缘检测
- `lab_ex3_osd`：HDMI 输出前的 OSD 叠加

整合版额外提供：

- KEY1 实时切换 RAW / EDGE 算法
- KEY2 / KEY3 调节摄像头曝光
- OSD 显示安路 Logo、动态文字、帧计数和当前算法状态
- 115200-8-N-1 UART 调试日志
- 边缘检测改为全分辨率梯度 + 灰度输出（见第 4 节），已上板验证
- 输出分辨率升级到 1280x720@60（见第 10 节），各级参数已同步，已上板确认

## 2. 系统数据流

```text
MIPI 摄像头
  -> MIPI D-PHY RX
  -> CSI / RAW10 解包
  -> ISP（demosaic -> AWB）
  -> 边缘检测（edge_detect_96）
  -> RAW / EDGE 算法选择 MUX
  -> DDR2 帧缓存
  -> HDMI 时序
  -> hdmi_mixer（Logo + 动态文字 + 帧计数 + 算法状态）
  -> hdmi_tx
  -> 显示器
```

RAW 路径和 EDGE 路径并行工作，MUX 在按键切换后选择其中一路送入 DDR。

## 3. 按键定义

| 板载按键 | 顶层信号 | 引脚 | 功能 |
|----------|----------|------|------|
| KEY1 | `I_button[1]` | D5 | RAW / EDGE 算法切换 |
| KEY2 | `I_button[0]` | A9 | 曝光目标值递减 |
| KEY3 | `I_button[2]` | B9 | 曝光目标值递增 |

KEY1 采用约 20 ms 消抖，短按一次切换一次算法。KEY2、KEY3 当前为短按调节，
不支持长按连续调整。KEY4 暂未使用。

## 4. 边缘检测实现

`user_source/hdl_source/isp/edge_detect_96.v` 相对官方实现有三处结构改动（前两处
来自 `feat/edge-magnitude`，第三处来自 `feat/edge-luma`）。输入输出仍是
96 位 × 4 像素/拍，`O_tuser` / `O_tlast` / `O_tvalid` 与数据严格对齐，但本版总
延迟为 2 拍，且输出的 4 个像素对应列 4k-1..4k+2，因此整幅边缘图相对 RAW
**左移 1 像素**。

1. **全分辨率梯度**。官方实现先做 `grp_gray = (gray0+gray1+gray2+gray3)>>2`，
   把同拍 4 个像素平均成一个再做 Sobel，真正参与梯度运算的是宽度只有 1/4 的图
   （1024x600 下是 256×600，现在 720P 下是 320×720），
   结果再复制回 4 个像素。宽度小于 4 像素的竖线因此被 4 倍组平均压到阈值以下
   而完全消失。本版为每个像素单独算 Sobel（4 路并行）。
2. **输出梯度灰度而不是硬二值化**。`I_thresh` 只作噪声门限，门限以上保留灰阶：
   `显示灰度 = clamp((|gx|+|gy|) << EDGE_GAIN_SHIFT)`，干净阶跃边缘是
   `|gx|+|gy| = 4Δ`（Δ 是两侧的真实灰阶差）。**门限决定“多弱才看得见”，增益决定
   “多强才全白”**：TH=16 → Δ≥4 可见，TH=48 → Δ≥12 才可见；增益 0 → Δ≥64 饱和，
   增益 1 → Δ≥32 饱和。当前取 TH=16 + 增益 0。
   同时删掉了三点多数滤波，它会把细笔画产生的孤立边缘像素直接抹掉。
3. **灰度公式换成官方 720P 例程的 `R/4 + G/2 + B/4`**（最大 253，不回绕、不用除法）。
   旧公式 `(R+G+B)/3` 的加法在 8 位表达式里先回绕，把全图**绝对亮度**压到 0..85
   （R=G=B=128 只剩 42、255 只剩 84）。
   **但它并不压缩局部对比度**：旧公式是斜率恒为 1 的锯齿，段内相邻像素的差分原样
   保留（实测 Δ=8 时 232/248 个相邻位置保留），只在每 85 级跨段时冒出 ±85 的假跳变
   ——那会在平滑表面上产生成片假边缘（白块/弧线）。所以换公式的实际收益是
   “去掉回绕假边 + 绝对亮度正确 + 少一个除法”，**不能**据此把门限或增益按 3 倍去
   换算。这一点踩过坑：一度把 TH 放大到 48，上板后弱边缘整片消失、只剩强轮廓。

幅度对比（下表是 **1024x600 + 旧灰度公式** 下的历史数据，用来比较“组平均 vs 全
分辨率”的几何差异，不代表当前配置的数值）：

| 竖线宽度 | 官方组平均版 | 原 `EDGE_TH=132` | 全分辨率版（门限 16） |
|----------|--------------|------------------|------------------------|
| 1 像素   | 40           | 消失             | 168                    |
| 2 像素   | 84           | 消失             | 252                    |
| ≥3 像素  | ≥124         | 3 像素仍消失     | ≥252                   |

上表是 Sobel 幅度本身（旧公式的压缩域）。两版的局部差分基本一致，所以新公式下
这些幅度也差不多；旧公式多出来的 ±85 假跳变会让部分区域直接饱和成白块，这正是
旧版图里那些成片白色细节的来源。

上板 A/B 对比（第一步：组平均 + 增益 2 / 第二步：全分辨率 + 增益 0）的结论：
**第一步的笔画更粗，但两版明暗肉眼分辨不出**。粗笔画说明第一步那种"更好看"
有相当一部分来自组平均把边缘摊成 4 像素的副作用；明暗无差异说明真实笔画宽度多在
3 像素以上、两版都已接近饱和。因此保留全分辨率几何，把增益调回 1。

历史配置（全分辨率 + 旧公式 + 增益 1 + 门限 16）在 1024x600 与 720P 两种分辨率下
都已上板测试、细笔画效果良好。当前配置（全分辨率 + 官方 luma 公式 + 增益 0 +
门限 16）已通过 TD（`main` @ `f6903de`，final Setup WNS +596 ps / Hold +20 ps、
0 违例），bitstream 在
`td_project/camera_to_dsi_display_Runs/phy_1/camera_to_dsi_display.bit`；
**已上板确认（2026-09-12），效果优秀**：原先的观察重点（弱边缘/印刷细节是否与旧版
相当、旧公式那种回绕假边是否消失）都已合格，这一版就是当前基线。

行缓存改成**三块按行轮转的 block RAM**：每块 320×48 位（1024x600 时是 256×48，
行缓存按 `IMG_WIDTH/4` 自动跟着分辨率走），保存一行内 6 个平滑灰度
（对应列 4k-2..4k+3），每周期只写其中一块、只读另外两块，读写永不同址且读地址已
寄存。这是必需的——全分辨率下若沿用官方那种异步读写法，行缓存会落成触发器，直接
把器件 FF 资源耗尽（TD 报 `PHY-9002 Placer initialization failed`）。改成 BRAM
后最终时序反而由负转正。

官方实现保留的已知限制：

- （旧实现遗留，本版已修）灰度计算 `R+G+B` 在 8 位表达式里回绕后再除以 3，会产生
  约 85 为周期的锯齿并把全图亮度压到 0..85（上表幅度偏小即由此而来）；
- `data96_128` 的 128 位打包计数器不会被帧起始单独复位。

任何进一步的数值“修正”都必须保持 `O_tuser` / `O_tlast` 与数据对齐，
并用固定文字目标做整幅边缘图对比后再替换，不能只比较“是否能检测到边缘”。

## 5. OSD 与画面状态

`hdmi_mixer.v` 负责在 HDMI 数据输出前叠加：

- 左上角：安路 Logo；
- 中部：动态文字和帧计数；
- 右上角：当前算法状态 `RAW` / `EDGE`。

算法状态文字位置由 `STATUS_OSD_X`、`STATUS_OSD_Y` 参数控制。切换算法瞬间
可能出现短暂的一帧撕裂，下一帧恢复属于当前设计的预期现象。

720P 下这几处坐标也调过：动态文字/帧计数 `DYN_OSD_X = 540`（1280 宽下水平居中），
右上角的 RAW/EDGE 状态字 `STATUS_OSD_X = 1100`，Logo 仍在左上角 160x160。

Logo 的 ROM 地址原来是 `S_logo_y * LOGO_W`，会被综合成一个 DSP 乘法器，而
`mult0 → Logo ROM → O_hdmi_data_reg` 正好是 75MHz 像素域上最紧的一条路径（TD 报
Setup 差 99 ps 就落在它上面）。`LOGO_W = 160 = 128 + 32`，现在写成移位加法
`((y<<7) + (y<<5)) + x`，数值完全等价、少用一个 DSP，这条路径也不再是瓶颈。

## 7. 串口运行时日志

开发板 Type-C USB 带有 USB 转 UART，FPGA TXD 使用 H1 引脚。日志格式为
115200-8-N-1，每秒输出一行：

```text
DBG:F=xxxx A=xxxx G=xxxx T=xxxxxx N=xxxxx B=xxxxx C=xxxxx M=xxx L=xx
```

字段含义：

- `F`：HDMI 显示帧计数
- `A`：AE 曝光目标值
- `G`：AG 增益目标值
- `T`：24 位流水线状态位图，定义见 `debug_uart_logger.v` 顶部注释
- `N`：当前帧非零像素计数
- `B`：亮度不低于 64 的像素计数
- `C`：亮度不低于 128 的像素计数
- `M`：RAW10 最大值
- `L`：显示层最大值

`N` / `B` / `C` / `M` / `L` 都是**上一完整帧**的统计：计数器在帧首锁存后清零，所以
同一行里的字段最多只差一帧，可以安全地拿去做 A/B 对比。

EDGE 模式下显示层是梯度灰度，所以 `N` / `B` / `C` 实际是 mag ≥ 16 / ≥ 32 / ≥ 64
的像素计数，可直接用来选边缘门限，不必只靠肉眼看画面。

读取日志：

```powershell
.\tools\read_debug_uart.ps1 -Port COM3
```

脚本会同时打印到终端并追加写入 `debug_uart.log`。

日志模块里的两个位宽都从参数推导（`debug_uart_logger.v` 的 `CLK_PER_BIT_W`、
`LOG_TICKS_W` 用 `$clog2` 算），**不要写死**——720P 升级把 `CLK_HZ` 从 52 MHz 改成
75 MHz 时踩过这个坑：

- 115200 的分频值是 651，而 `S_tx_div` 当时只有 9 位（0..511），比较永不成立，
  状态机进 `TX_START` 后就停在起始位、TXD 恒低，日志完全不再输出；
- `TIMEOUT_CNT` 当时写死 26 位，74,999,999 被截断成 7,891,135；即使修好分频，
  日志周期也只有 0.105 s 而不是 1 s。

分频值同时从 `ceil` 改成四舍五入（651，误差 +0.006%；`ceil` 得到的 652 是 -0.15%）。
同一个函数里 `F_line_byte` 的 case 标签也必须写成 `7'd64..7'd68`：写成 6 位字面量
时值会退化成 0..4 并落进 `default`，`L` 字段整段发的是空格、CR 也没了。
这一版已在板上确认：日志恢复正常输出，分频、1 s 周期和 `L` 字段都对。

2026-09-12 又补了两个后来才发现的坑（都先在 `feat/edge-denoise` 分支上修好，再摘到
`main`）：

- **同一行的字段必须取自同一帧**。一行 70 字节按 115200-8-N-1 要发约 6 ms，而一帧
  只有 16.5 ms，1 s 的日志节拍又和 60.6 fps 不同步：以前 `N/B/C/M/L` 是边发边采样的，
  落在帧内不同时刻——板上出现过 `B > N`（同一个快照不可能），`M` 在相邻行之间
  1023/247/1023 反复跳。现在 `design_top_wrapper.v` 在帧首（显示器帧 `S_hdmi_user`、
  相机帧 `S_raw_tuser`）先把计数器搬进 `*_hold` 寄存器再清零，日志只报上一完整帧。
- **`tools/read_debug_uart.ps1` 在 Windows PowerShell 5.1 上会先报错再正常工作**：
  脚本原来无条件执行 `Add-Type -AssemblyName System.IO.Ports`，而 5.1、PowerShell
  7.0~7.3 下这个程序集找不到（`ASSEMBLY_NOT_FOUND`），类型本身却已经可用。现在改成
  先探测类型、再按路径加载、最后才报错；选口改用
  `[System.IO.Ports.SerialPort]::GetPortNames()`（`Win32_SerialPort` 在部分环境查不到，
  会误报 No serial port found），并新增 `-ProbeSec` 体检模式（打印原始字节数与 hexdump，
  用来区分“线上一个字节都没有”和“收到乱码”）；脚本保存为带 BOM 的 UTF-8，否则
  PowerShell 5.1 会把里面的中文按 GBK 解码。

这两处的 TD 结果：**final Setup WNS +242 ps / TNS 0 / 0 违例，Hold +20 ps / 0 违例，
slices 16957（79.93%）**；脚本已在 PowerShell 5.1 实测不再报错。

**帧首锁存已在板上确认（2026-09-12，同一画面的 12 行日志）**：

- `N` 在 19634~20018（±1%）、`B` 2588~2667、`C` 645~666、`M` 722~831 之间小幅波动，
  相邻行不再成倍跳变；此前出现过的 `B > N`（892294 > 790449）彻底消失，`N` 也不再
  在 4633~33109 之间乱窜——说明一行里的字段确实取自同一个完整帧。
- `F` 每行递增 60~61（0x3C / 0x3D），与 60.6 fps、1 s 节拍一致；`L=FF` 正常输出，
  分频 / 周期 / `L` 字段那三个修复同时得到确认。

## 9. 当前已知风险

- 边缘实现已改为全分辨率梯度 + 灰度输出，画面与官方例程不同；1024x600 与 720P
  都已上板确认细笔画效果良好、画面无异常（无 4 像素梳状纹理、无水平错位），但
  **尚未做与固定文字目标的整幅边缘图数值对比**，边缘质量目前仍是主观确认；
- 720P 是本工程第一次跑的模式：摄像头寄存器表取自官方 `lab_ex*_SC500_720P` 例程，
  已上板实测合格。以后若改 sensor 窗口/帧率、PLL 或 HDMI 时序，必须按第 10 节的
  对照表整链一起改，并重新综合与上板确认；
- 边缘图相对 RAW 左移 1 像素、总延迟 2 拍，这是设计选择而非缺陷；
- 官方和整合版都没有完整的 ready/backpressure 闭环，DDR 或 FIFO 拥塞时
  需要重点检查数据是否被丢弃；720P 的 DDR 读写量比 1024x600 高 50%（写+读约
  330 MB/s），上板实测画面稳定，但长时间运行或加大算法负载时仍要用 `DBG:` 日志
  的帧计数和 N/B/C 复查有没有丢帧；
- 时序余量一直很薄：720P 上出现过 Setup **-99 ps**（只差一个端点）的版本。而且
   TD 的布局布线是确定性的——同一份网表重跑，HPWL、拥塞和时序数字完全一样，
  不能指望“再跑一次就好了”，只能改逻辑或改约束。去掉 `hdmi_mixer` 里那个 DSP
  乘法器后，TH48 那版是 Setup +728 ps；`main` 上的 TH16 版是 +596 ps（0 违例）。
  余量对布局落点很敏感，继续加功能后必须重新确认；
- 当前配置是“新公式 + TH16 + 增益 0”，已通过 TD（final Setup WNS +596 ps、0 违例）
  并已上板确认（2026-09-12），效果优秀：弱边缘与旧版相当、旧公式的回绕假边消失，
  这一版是当前基线。增益 0/1 的取舍（饱和点 Δ≥64 vs Δ≥32）还没做板级 A/B 对比，
  只是可选的调优方向，不影响当前基线；
- 调 TH / 增益时**不要按灰度公式换算**：公式改的是绝对亮度，Sobel 只看局部差分，
  两者不是一回事——TH 48 那一版就是这么踩的坑，弱边缘被整片拦掉。

## 10. 分辨率与时钟配置（720P）

2026-09 起整条链路从 1024x600 升到 **1280x720@60，75 MHz 像素时钟**。分辨率是
整链参数，不能只改一处；改动时对照下表一起改，改完必须重新综合与布局布线。

| 环节 | 现在（720P） | 之前的 1024x600 |
|------|--------------|-----------------|
| 摄像头窗口 | 1280x720，起点 (512,512)，HTS 1600 / VTS 1000，VBIN+HSUB，2-lane 约 480 Mbps | 1024x600，起点 (1024,1024)，HTS 2852 / VTS 1127 |
| 摄像头寄存器表 | `uics500reg.v`（模块名不变，内容取自官方 `lab_ex*_SC500_720P` 例程） | 旧表 |
| PLL | C4 75 MHz（像素）/ C5 375 MHz（TMDS serial）/ C1 23.81 MHz（摄像头 MCLK 与 I2C） | C4 52 / C5 260 / C1 24.07 MHz |
| VTC | 1280x720，帧 1650x750，sync 1390/1430、725/730 | 1024x600，帧 1344x635 |
| HDMI TX core | HTOTAL 1650 / HSA 40 / HFP 110 / HBP 220 / VTOTAL 750 / VSA 5 / VFP 5 / VBP 20 | 1344 / 24 / 160 / 136、635 / 2 / 12 / 21 |
| ISP、边缘、裁剪、uial2axis、hdmi_mixer | 全部 1280x720 | 1024x600 |
| MIPI 输入约束 | `mipi_rx_ck_pad` period 4.167ns（480 Mbps/lane，CSI 域实测 59 MHz） | period 2.222ns（过度约束） |
| 串口日志 | `CLK_HZ = 75000000` | 52000000 |

摄像头寄存器表的顺序也要留意：出厂文件要求先写 `0x0100=01`（stream on，索引 114），
等 10 ms 再写 `0x302d=00`（索引 115），这个延时由 `uicfgcs500.v` 里的
`POST_STREAM_DELAY` 实现，换表时不要丢掉。

构建结果（TD Release_2026.1_SP2，`main` @ `0ec7385`，新公式 + TH16 + 增益 0，含第 7
节的串口日志修复与帧首锁存）：**final Setup WNS +242 ps / TNS 0 / 0 违例，
Hold WNS +20 ps / 0 违例**，slices 16957（79.93%）、RAM 39、DSP 8。时序余量对
布线落点很敏感（同一设计的 TH48 版 +728 ps、`feat/720p` 首版 +271 ps、
`feat/edge-luma` 那版 +9 ps、帧首锁存前的 `main` +596 ps），但都 0 违例。bitstream：
`td_project/camera_to_dsi_display_Runs/phy_1/camera_to_dsi_display.bit`。

**已上板确认**：1280x720 画面正常、RAW/EDGE 切换与曝光按键可用、OSD 位置合适，
720P 改造到此完成。后续再调算法参数时，用 `tools/read_debug_uart.ps1` 读 `DBG:`
日志（帧计数、N/B/C）做客观对比。

## 11. 资源占用与优化方向

### 11.1 现在的占用（`main` @ `0ec7385`，2026-09-12 的构建）

| 资源 | 用量 | 占比 | 说明 |
|------|------|------|------|
| slices | 16957 | **79.93%** | 器件共 21216 个 slice |
| LUT6 | 14972 | 70.57% | TD 的 `#lut6` 口径 |
| 触发器 | 14356 | 33.83% | 分母 42432（每 slice 2 个 FF） |
| 分布式 RAM（占 slice） | 1560 | — | 1448 LUTRAM + 112 SRL |
| ERAM | 39 | 36.11% | 还剩 69 块 |
| DSP | 8 | 20.00% | 还剩 32 个 |
| feedthrough | 6809 | — | 官方 720P 例程只有约 2400 |

slice 的构成：1560（分布式 RAM）+ 10134（带 LUT 的逻辑）+ 3278（加法器/进位链）+
1985（只有 FF 的 slice）= 16957，最后那 1985 个就是打包开销，占 11.7%。官方
lab_ex1 / lab_ex2 / lab_ex3 的 720P 版本分别是 20.2% / 19.4% / 14.7%，所以我们
的打包效率是这几个里最紧的——**继续压 slices 只能靠真删逻辑，别指望编译选项**。

两个容易搞混的口径：数据手册表 1-1 里 PH1P35 写的是 **LUT4s 38,189**，那是 LUT4
等效口径（= 21216 × 1.8）；TD 报告里的 `#lut6` 是物理 6 输入查找表位点数。同一份
资源、换算比 1.8，利用率两种口径算出来一样；手册同表的 DFFs 42,432、ERAM 108、
DSP 40 与 TD 报告的容量完全一致，可以互相印证。

### 11.3 优化方向（按性价比排序）

| 手段 | 估算收益 | 风险 |
|------|----------|------|
| 分布式 RAM 搬进 BRAM（BRAM 还剩 69 块） | −800 ~ −1200 slices | 中：BRAM 读延迟 1 拍、写模式受限，要同步改流水线 |
| Logo/文字 ROM 搬 BRAM | −200 ~ −600 | 低 |
| 精简调试/观测逻辑（UART logger、N/B/C/M/L 统计） | −200 ~ −500 | 低，功能可保留（抽样或复用计数器） |
| 宽通路重构（96 位 × 4 像素延迟线、RAW/EDGE 双路径 mux、常量乘法移位化） | −200 ~ −600 | 中高：必须守住第 4 节的流水线相位 |
| 打通拥挤、回收 feedthrough（打包选项、拆大 mux、减少跨区走线） | −300 ~ −1000 | 高：最不确定，得反复试落点 |

预期结果：**现实目标约 70%（≈14.8k slices）**，即把比官方最全例程多出来的 1775
slices 基本吃掉；继续做到 **64%~66%（13.5k~14k）** 需要上面几项都做一遍。低于
60%（<12.7k）不现实——官方纯 MIPI+DDR+HDMI 的 720P 例程本身就有 58.25%。

### 11.4 余量策略与操作注意事项

- 密度上限：**≤80% 舒适，85% 可接受，90% 是红线**。官方例子在 58%~70%，我们现在
  79.93%，已经贴着 80% 这条线——再动功能之前必须先腾资源。
- 评估“还能加多少功能”用 **1 个 LUT6 ≈ 1.13 个 slice**（含约 12% 打包开销）：到 85%
  还能加约 1080 slices（≈950 LUT6），到 90% 约 2140 slices（≈1880 LUT6）。
- 比百分比更该盯的三个指标：**final Setup WNS**（建议 ≥ +300 ps 才当基线）、
  **feedthrough**（继续涨说明布线在恶化，比 slices 更早预警）、以及**能否一次
  布局布线成功**（要反复重跑就说明余量不够）。
- 新增行缓存/延迟线一律写 `(* ram_style = "block" *)`（`edge_detect_96.v` 已经这么
  写）。历史上行缓存落成触发器直接把 FF 打满，TD 报 `PHY-9002 Placer initialization
  failed`——这个流在资源满时是“编不出来”，不是“编得慢”。
- 看资源数字请认**本次运行**的 `td_YYYYMMDD_HHMMSS.log` 与 `*.area`：`phy_1\run.log`
  可能是更早构建留下的旧文件（本项目就误读过一次，把 8 月的数字当成当次结果）。
  目前还没有分层次面积报告，要定位具体模块可以在 TD 里跑 `report_area -hier`。
- 想加功能又不想吃 slice 时，优先用富余的块资源：ERAM 还剩 69 块、DSP 还剩 32 个，
  “把逻辑换成 BRAM/DSP”是本设计最现实的资源来源。
