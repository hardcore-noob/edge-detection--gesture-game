### 11.1.2 资源优化第二版：精简调试/观测逻辑（第一批，2026-09-12）

只做了"语义不变"的那一半，第二批（T 字段瘦身）和第三批（N/B/C 抽样、删 A/G）
因为性价比太低被用户否掉，不再做。这一批改了两处：

1. **删掉 logger 的 9 组输入双寄存器**（约 300 个 FF）。`debug_uart_logger` 的

   里（整帧稳定）。原写法是从"logger 跑在另一个时钟域"的年代留下来的。

### 11.1.3 资源优化第三版：行缓存搬 ERAM（2026-09-12）

11.3 表里剩下最大的一块：`edge_detect_96` 的三块行缓存（面积表 `dram lut = 1152`）。
做法与 Logo ROM 同一套路 —— TD 不认 `ram_style` 属性，必须显式例化
`PH1P_LOGIC_ERAM`；这次把它收成通用封装 `user_source/hdl_source/eram_spram.v`
（单口、1 拍读延迟、`FILL_ALL("0")`），三块缓存各例化一个。

时序上是"纯换存储介质"：原写法 `mid_r <= line_memN[x_grp]` 本来就是"地址寄存 + 数据
打一拍"，正好等于 ERAM 的 `REGMODE_A="OUTREG"`，所以改动只在于：

- `mid_r` / `top_r` 从寄存器改成直接引 ERAM 输出（**不再多打一拍**）；
- 读侧选择用**上一拍**的轮转相位（`row_phase_d1`），因为地址是在那一拍给出的；
- 写数据 `sm0..sm3` / `win_cur` 从 always 块里的变量提成显式线网 `S_sm0..S_sm3` /
  `S_win_cur`（否则写数据可能被当成寄存器、比写地址晚一拍，行缓存整体错 4 个像素）；
- 写使能带上 `I_rst_n`（原实现的写操作在 always 块的"非复位"分支里）。

**流水线深度与逐拍对齐完全没变**，理论上画面应与改前逐像素一致。

### 11.1.4 时序余量：place 的 opt_timing 提到 high（2026-09-12）

11.1.3 之后全局 WNS 掉到 +226 ps。用 `tools/build_td.ps1` 新加的"分时钟域余量"一看，
紧的根本不是我们写的逻辑：

| 路径组 | medium | high（本次） |
|--------|--------|--------------|
| HDMI_SERIAL_CLK -> 自身（375 MHz） | **0.226 ns** | 1.120 ns |
| HDMI_PIXEL_CLK -> HDMI_SERIAL_CLK | 0.876 ns | 1.086 ns |
| HDMI_PIXEL_CLK -> 自身（75 MHz，我们的逻辑） | 1.057 ns | 1.560 ns |
| MIPI_RX_BYTE_CLK / DDR usr_clk 等 | 5.0 ~ 37.8 ns | 5.0 ~ 37.4 ns |

最紧那条路径是 `u0_lane_lvds_8_1` 里从一个触发器到 IO 里 ODDR 输入：
**延迟 2.221 ns 里 net 占 2.006 ns（91%）、逻辑级数 0** —— 发射触发器被布局器摆到了
离 ODDR 13 列远的地方，纯走线问题。所以"拆大 mux / 打通全局拥挤"对它没用（没有逻辑
可拆，全局利用率也只有 61%），真正的杠杆是**落点**。

改法：Run 目录 `settings.cfg` 里加 `set phyWildParams {place opt_timing high}`
（默认 medium，见第 6 节）。一次布局布线之后：

| 指标 | medium | high |
|------|--------|------|
| 全局 final Setup WNS | +226 ps | **+866 ps** |
| slices | 13002（61.28%） | 12987（61.21%） |
| LUT6 / 触发器 | 10743 / 14032 | 10738 / 14036 |
| feedthrough | 6626 | 6513 |
| final Hold WNS | +20 ps（0 违例） | +20 ps（0 违例） |
| place / route 耗时 | 2m04s / 58s | 2m08s / 57s |

**结论**：遇到"余量薄"先看分时钟域余量和最紧路径的 net 占比，再决定是改逻辑还是改
落点。这条路径靠落点修，代价接近零；反过来，为了它去动全局打包/feedthrough 是白费力气。

> 说明：这次只改了布局参数、RTL 与综合网表都没动，所以逻辑功能与 11.1.3 那版逐位
> 一致，只是重新布局布线后的 bitstream。

### 11.1.5 观测增强：FIFO 丢写与占用进 DBG 行（2026-09-12，`4b1ec22`）

`video_in` / `video_out` 的 FIFO 原来在写满时**静默丢数据**，光看画面很难发现。这一版
把两边 FIFO 的丢写计数和每帧最大占用同步到显示域，按帧差上报成 DBG 行的
`D` / `E` / `W` / `V` 四个字段（读法见第 7 节）：`D`/`E` 非 0 就说明真的丢过数据，
`W`/`V` 接近 `0x1FF` 说明离写满很近。

### 附：Logo 地址的 DSP 乘法器（2026-09-10 前后）

Logo 的 ROM 地址原来是 `S_logo_y * LOGO_W`，会被综合成一个 DSP 乘法器，而
`mult0 → Logo ROM → O_hdmi_data_reg` 正好是 75MHz 像素域上最紧的一条路径（TD 报
Setup 差 99 ps 就落在它上面）。`LOGO_W = 160 = 128 + 32`，现在写成移位加法
`((y<<7) + (y<<5)) + x`，数值完全等价、少用一个 DSP，这条路径也不再是瓶颈。

## 串口日志

字段语义与脚本用法见 README 第 7 节；这里记成因、改法和上板验证数据。

### 1. 分频位宽：9 位装不下 651 的分频值

日志模块里的两个位宽都从参数推导（`debug_uart_logger.v` 的 `CLK_PER_BIT_W`、
`LOG_TICKS_W` 用 `$clog2` 算），**不要写死**——720P 升级把 `CLK_HZ` 从 52 MHz 改成
75 MHz 时踩过这个坑：

- 115200 的分频值是 651，而 `S_tx_div` 当时只有 9 位（0..511），比较永不成立，
  状态机进 `TX_START` 后就停在起始位、TXD 恒低，日志完全不再输出；
- `TIMEOUT_CNT` 当时写死 26 位，74,999,999 被截断成 7,891,135；即使修好分频，
  日志周期也只有 0.105 s 而不是 1 s。

分频值同时从 `ceil` 改成四舍五入（651，误差 +0.006%；`ceil` 得到的 652 是 -0.15%）。
同一个函数里 `F_line_byte` 的 case 标签也必须写成 `7'd64..7'd68`：写成 6 位字面量
时值会退化成 0..4 并落进 `default`，`L` 字段整段发的是空格、CR 也没了。
这一版已在板上确认：日志恢复正常输出，分频、1 s 周期和 `L` 字段都对。

### 2. 帧首锁存与 PowerShell 脚本

2026-09-12 又补了两个后来才发现的坑（都先在 `feat/edge-denoise` 分支上修好，再摘到
`main`）：

- **同一行的字段必须取自同一帧**。一行 70 字节按 115200-8-N-1 要发约 6 ms，而一帧
  只有 16.5 ms，1 s 的日志节拍又和 60.6 fps 不同步：以前 `N/B/C/M/L` 是边发边采样的，
  落在帧内不同时刻——板上出现过 `B > N`（同一个快照不可能），`M` 在相邻行之间
  1023/247/1023 反复跳。现在 `design_top_wrapper.v` 在帧首（显示器帧 `S_hdmi_user`、
  相机帧 `S_raw_tuser`）先把计数器搬进 `*_hold` 寄存器再清零，日志只报上一完整帧。
- **`tools/read_debug_uart.ps1` 在 Windows PowerShell 5.1 上会先报错再正常工作**：
  脚本原来无条件执行 `Add-Type -AssemblyName System.IO.Ports`，而 5.1、PowerShell
  7.0~7.3 下这个程序集找不到（`ASSEMBLY_NOT_FOUND`），类型本身却已经可用。现在改成
  先探测类型、再按路径加载、最后才报错；选口改用
  `[System.IO.Ports.SerialPort]::GetPortNames()`（`Win32_SerialPort` 在部分环境查不到，
  会误报 No serial port found），并新增 `-ProbeSec` 体检模式（打印原始字节数与 hexdump，
  用来区分“线上一个字节都没有”和“收到乱码”）；脚本保存为带 BOM 的 UTF-8，否则
  PowerShell 5.1 会把里面的中文按 GBK 解码。

这两处的 TD 结果：**final Setup WNS +242 ps / TNS 0 / 0 违例，Hold +20 ps / 0 违例，
slices 16957（79.93%）**；脚本已在 PowerShell 5.1 实测不再报错。

**帧首锁存已在板上确认（2026-09-12，同一画面的 12 行日志）**：

- `N` 在 19634~20018（±1%）、`B` 2588~2667、`C` 645~666、`M` 722~831 之间小幅波动，
  相邻行不再成倍跳变；此前出现过的 `B > N`（892294 > 790449）彻底消失，`N` 也不再
  在 4633~33109 之间乱窜——说明一行里的字段确实取自同一个完整帧。
- `F` 每行递增 60~61（0x3C / 0x3D），与 60.6 fps、1 s 节拍一致；`L=FF` 正常输出，
  分频 / 周期 / `L` 字段那三个修复同时得到确认。

### 上板 A/B 结论与历史配置

上板 A/B 对比（第一步：组平均 + 增益 2 / 第二步：全分辨率 + 增益 0）的结论：
**第一步的笔画更粗，但两版明暗肉眼分辨不出**。粗笔画说明第一步那种"更好看"
有相当一部分来自组平均把边缘摊成 4 像素的副作用；明暗无差异说明真实笔画宽度多在
3 像素以上、两版都已接近饱和。因此保留全分辨率几何，把增益调回 1。

历史配置（全分辨率 + 旧公式 + 增益 1 + 门限 16）在 1024x600 与 720P 两种分辨率下
都已上板测试、细笔画效果良好。当前配置（全分辨率 + 官方 luma 公式 + 增益 0 +
门限 16）已通过 TD（`main` @ `f6903de`，final Setup WNS +596 ps / Hold +20 ps、
0 违例），bitstream 在
`td_project/camera_to_dsi_display_Runs/phy_1/camera_to_dsi_display.bit`；
**已上板确认（2026-09-12），效果优秀**：原先的观察重点（弱边缘/印刷细节是否与旧版
相当、旧公式那种回绕假边是否消失）都已合格，这一版就是当前基线。

### 阶段 4：KEY1 切到 EDGE 但画面不变——提交字位序取反（2026-09-14 上板发现并修复）

**现象**：按 KEY1 后右上角字样变成 `EDGE`，但画面仍是 RAW。

**根因**：模式提交字是 `{display_mode[3:0], edge_th_sel[3:0]}`（display_mode 在高 4 位），
而顶层消费侧写成按 `bit0` 取算法位、按 `bit7:4` 取门限档位——**两段正好取反**：
alg mux 拿到的是"门限档位的最低位"，默认恒 0，所以无论怎么按都停在 RAW；OSD 用的是
像素域的**请求值** `display_mode`，所以字样照常翻转。同一个错误也让"生效门限"取错
（`S` 字段会跟着 display_mode 走）。

**修法**：

- 顶层引入具名线网 `S_committed_display = S_mode_committed[7:4]`、
  `S_committed_th_sel = S_mode_committed[3:0]`，所有消费者（alg mux、生效门限、
  DBG 的 S 字段）改用它们，不再手写下标；
- `mode_sync.v` 头注释里把布局写死（哪一段在哪几位、谁该取哪几位）；
- 顺手加固：**OSD 状态字与 T 位图 bit3 改用已提交的 display_mode**（不是请求值），
  这样"右上角字样"永远等于屏幕上真正在放的那一路——以后即使提交通路出问题，也会
  表现为"字样不跟着按键变"，而不是这次这种"字样变、画面不变"的误导。

**这个 bug 只有上板才看得见**：`U`/`X`/`Y` 那些自检字段全是对的信号（它们不经过
模式字），构建、时序、资源也都正常。教训：跨域提交这种"两边各取一半"的地方，一定
要用具名线网拆位并在模块头注明布局，别在两处各写一遍下标。

**② 修掉一条被掩盖的 0.268 ns 路径（这才是初版 WNS 掉的真正原因之一）**

初版把 logger 行模板从 96 字节加长到 152 字节后，24 MHz 的曝光值 `A`/`G` 变成
`u_ae_set/r_ae_reg → logger 模板组合逻辑 → S_tx_byte` 这样一条 **6 级组合**的长路径，
卡在 SDC 里原有的 `set_max_delay -datapath_only 5.000 -from pll_clk_24m -to HDMI_PIXEL_CLK`
上，slack 只剩 **0.268 ns**，成了全设计最差 setup，把真正的片内最差路径盖住了。
修法：在顶层把 `S_ae`/`S_ag` 先在像素域打一拍再送 logger，那条跨域路径退回 FF→FF。

**顺带纠正一条 SDC 认知（重要，别再踩）**：我一开始给新加的 CSI↔像素域通路也写了
`set_max_delay -datapath_only 5.000`，实测**TD 直接忽略**——报告
`camera_to_dsi_display_exception.timing` 里这两条被标成 `Set Max Delay (Ignored)`，
把 5.000 改成 15.000 后**所有时序数字一个都没变**。原因是这两个时钟在 SDC 开头就是
两个异步组，组间路径本来就被切断。也就是说：**CSI 域 ↔ 像素域之间的时序 TD 根本不查**，
那两条约束现在只起"记录意图"的作用（万一以后取消异步组就立刻生效），真正的保障只能是
握手设计本身（toggle 两级同步 + 数据先稳定后整包捕获）。而 24m↔像素域虽然也"异步"，
却在**同一个组**里，所以照常按普通路径算——那类路径必须靠打拍/RTL 去满足。

每次只跑布局布线（`-Stage phy`，syn 的网表不变），参数写在 `phy_1/settings.cfg` 的

### 阶段 6：观测字段恒 0——tuser 被错误地闸在 valid 里（2026-09-15 上板发现并修复）

**现象**（用户上板抓的一行行 `DBG:`）：`F/A/G/T/N/B/C/M/L/D/E/W/V/K/S/X/Y` 全部正常，
唯独 `U=P=Q=R=0000`。CTRL_SYNC 往返（`X/Y`）与模式提交（`K/S`）都对，说明 logger 的
字段机制和跨域通路都没问题，问题出在 VIDEO_TAP 那一包。

**根因**：`awb.v` 里 tuser 是**不带延迟直通**的（`assign O_tuser = I_tuser;`），而 valid
是流水后的、并且行间有空隙——同一个文件里 `assign O_tlast = (valid_d1==0)&&(valid_d2==1)`
就是靠 valid 的空隙检测出"每个行首"的。所以 tuser 脉冲经常落在 valid=0 的拍上。而我在
`recog_top` 里把三处帧锁存**都闸在了 tvalid 上**：

- toggle 写成 `I_edge_tvalid && I_edge_tuser` → 脉冲被吞 → toggle 不翻转 → 像素域的
  "整包捕获"从不触发；
- tap 写成 `if(I_raw_tvalid) … if(I_raw_tuser)` → 计数与锁存都不发生；
- `mask_stats` 整块写成 `else if(I_valid)` → 帧首锁存与清零都不发生。

三处叠加，`U/P/Q/R` 就恒为 0；而 `X/Y` 走 ctrl_sync（不经过这个闸门）所以照常正常——
这正是把线索指向"闸门"而不是"数据"的关键。

**修法**：帧锁存一律与 valid 解耦——toggle 只看 `tuser`；tap 的**计数按 valid、锁存按
tuser**；`mask_stats` 的帧首分支移出 `if(I_valid)`（帧首那拍若同时有有效像素，仍按第 0 组
累加，用 `S_new` 选择初值）。

**教训**：这是典型"只有上板才暴露"的问题——构建、时序、资源全正常，`U=0x384` 的理论值也
算得出来，但没有真机数据就发现不了；而且它不影响画面，只让观测字段失效，很容易被忽略。
**新增任何帧级计数/锁存时，先把 tuser 与 valid 的相位关系确认清楚（见 README 第 12.4 节）。**

## 2026-09-25（续 3）　打磨②：肤色判据 v2 + 帧内色度上报（诊断 bit）

## 2026-09-25（续 4）　打磨③：全局亮度补偿（治"光照一变就全屏在动"）

"在动"——运动门从此不再区分"手"和"背景"，红/黄（需要 肤色∩运动）也就被那层绿盖住。
（用户同时确认：**原摄像头画面本身是正常的**，所以不是颜色链路的问题。）

**改动**（`recog_top.v`，默认 `GLB_COMP=0` = 原行为）

  **平移而不是重采样**——重采样会把静止的手吃进背景，平移保留"手 vs 背景"的对比度。
- 平移用 10 位补码位型相加再钳到 0..255（避开 Verilog 混合符号表达式的坑）。

## 2026-09-25（续 10）　修正 `M1_BEST_20260925.bit`：恢复"肤色 ∧ 运动"双门

## 2026-09-25（续 11）　治"静止时准星乱动"（死区 + 丢失冻结 + 最大尺寸门）

## 2026-09-26　软权重（SOFT_TRACK）+ 治"不灵敏"

## 2026-09-26（续）　软权重 + ROI 门控 + 背景差运动门（治"准星不跟手"）

## 2026-09-26（续 3）　第二步：治"灯照亮的桌面一片在动"（相对门限 + 背景自愈 + 采样加密）

**用户上板反馈**（`m1step16_view_sel_diag.bit` 的运行时视图）：切到**视图 4（只看运动门）绿色特别多**，

**根因（三条叠在一起，都在背景模型里）**
1. **旧的 quiet 门是个单向棘轮**（`S_quiet` 要求 `|采样−背景| < QUIET_TH(4)` 才允许蠕变，每次只走 1 格，

## 2026-09-26（续 4）　第三步：运动门换成"帧差 + 块级活动锁存"（治"亮区一片在动"的结构改法）

背景收敛到"块内均值"之后，块内比均值亮/暗超过门限的像素**永远是"在动"**。
**这是 16×16 模型的分辨率下限，不是阈值没调好**——自愈只会让背景更贴均值，误报一个都不少。

**另外修掉一个真 bug（顺手挖出来的）**：背景预取地址

**回卷到本行首块**，于是"每块行的第一个块（图像最左 16 像素）"用的是**上一行首块**的背景

1. **运动判据从"和背景比"换成"和上一帧比"**（块级帧差）：静态场景**结构上就是 0**，
   跟纹理、光照、块大小全都无关。`S_fd = (LATCH_MODE!=0) || FRAME_DIFF` 保证背景等于"上一帧的采样"。
2. **块级活动锁存**：一块的采样均值相对上一帧变化 > 门限 → 这块"在动" → 锁存计数器置满
   （`LATCH_MAX=15`），之后**每 4 帧减 1**（≈1.0 s）。手停住还兜得住，桌面不动就自然清零。
   存储：3600 块 × 4 bit = 1800 B → **1 块 2048×8 ERAM**（两块共用一个字节）；
   读时序与背景 RAM 同一套预取（上一块 phase==3 发地址 → 本块 phase 0 有效），写发生在 phase==2。
3. **掩码 = 肤色 ∧ 锁存**（`S_motion_mask` 直接换成锁存位）：手整体高亮（**肤色给面积**），
   静止场景没有锁存 → **0 误报**。软权重的运动分同样改成"锁存开着就算在动"，权重仍取 `min(肤色, 运动)`。
4. 自举期内（含"重建背景"窗口）锁存一律算"没动过"（`S_bg_ready`），避免空存储被判成活动。
5. 帧计数器 6→8 位（低 2 位当"每 4 帧"节拍）。
6. `LATCH_MODE=0` 可退回第二步的"逐像素和背景比"（保留做 A/B）。

### 算法（复用 M1 质心，不新增像素级统计）

1. **观测源**：M1 的质心 `S_cent_x/S_cent_y`（S1 已统一观测源）。相位：质心除法器在帧首后

   —— 相邻两次 tuser 采到的是相邻两帧质心，差就是帧间位移，不引入额外滞后。
2. **质心延迟线**：存最近 `GEST_WIN-1` 帧质心（d1/d2/d3）。**窗口净位移**
   `Δx = 本帧 − (GEST_WIN-1) 帧前`，`Δy` 同理。`GEST_WIN` 默认 4（实现支持 3/4）。
3. **判据**（`VX_TH=40`、`VY_TH=32`，单位 = 窗口净位移像素）：

4. **可信性门**：只有"本帧质心可信"**且**"窗口内每帧都可信"（连续可信帧数 ≥ GEST_WIN）才判

### 2026-10-11（续 2）　M2.1 第 2 轮：动作段状态机 + 下劈换"掩码最高行" + 余量判据

**用户上板反馈（`M2_WAVE_VIS` 实机）**：① 明明是横向挥手却出**蓝条**（误报下劈）；
② 有时**连续出三条颜色**（一个动作出多次事件）。用户给了三条修正方向，本轮照做并把
三个隐藏坑补上。

**1. 为什么横挥会误判成下劈（根因）**：上一版的下劈用**质心 y**：
`Δy = 质心行 − 4 帧前质心行`，门限 32。但质心是**面积中心** —— 横向挥手时手臂进/出 ROI、
掩码形状一变，质心就上下漂；横挥到两端一减速，|Δy| 常常大于 |Δx|，于是 `Δy>32 且 |Δy|>|Δx|`
当场成立 → 蓝条。**这是判据本身选错了信号，不是门限太小。**

**2. 本轮改的三件事（对应交流里那三条）**：

1. **动作段状态机（消灭"三色连出"）**：位移超 `GEST_START_TH`=8 px/帧 = 动作开始（记起点）；
   之后**连续 9 帧**（`GEST_QUIET_FRAMES`，≈150 ms）都安静（|位移| ≤ `GEST_QUIET_TH`=5 px/帧）
   才判"动作结束"，**在结束时按整段净位移一次性定性** —— 一个动作只出一个事件。
   另加 `GEST_SEG_MAX`=150 帧（≈2.5 s）强制结算，防"场景一直在动"永远卡在动作中。
2. **下劈换信号**：纵向改用 **mask_stats 现成的掩码最高行 `S_ymin`（11 位全精度）**，
   不再用质心 y。手往下劈 → 最高行明显下移；横挥 → 最高行基本不动。
   顺带修了一个**相位坑**：`y_min` 是 mask_stats 在 tuser 那一拍锁存的，所以那一拍**读到**的
   是再上一帧的值（比质心晚一拍）；实现里用"cx1/cx2 两级 + ym1 一级"把两条路对齐到同一对帧
   (k−1,k−2)，否则下劈位移会差一帧（约 10~20 px，正好吃掉 `|ΔX|<25` 这个余量）。
3. **判据换成明确余量**：左/右 = `|ΔX| > GEST_X_TH`(60) 且 `|ΔX| > 2·|ΔY|`；
   下劈 = `ΔY > GEST_Y_TH`(120) 且 `|ΔX| < GEST_Y_XMAX`(25)。两条都不满足但整段位移
   > `GEST_NOISE_TH`(30) → 闪**青色**（"看到动作、方向够不上"）；小于噪声完全不闪。
   同时**删掉了 300 ms 冷却**（状态机已经保证一次动作只结算一次）和上一版的"前半段同向"投票。

**3. 实测（一次 PnR 成功，0 违例）**：`13173 LUT6（62.09%）/ 15518 slices（73.14%）/
ERAM 71 / DSP 8 / Setup WNS +915 ps / Hold +20 ps / feedthrough 7298`。
相对上一版（13226 / 15506）**LUT6 −53** —— 4 级位移延迟线被"段起点 2 个寄存器 + 状态机"换掉了。

### 2026-10-11（续 3）　M2.1 第 3 轮：判据改"整段**峰值**"（消灭横挥误报下劈）+ 提示条画到屏幕边缘

**用户第 2 轮实机反馈**：左挥**仍然**会出蓝条，并质疑"三色条"这个形式；怀疑与镜头角度有关。

**根因（第 2 轮没解决的原因）**：第 2 轮把"下劈的纵向信号"换成了 `y_min`（这是对的），但
**位移口径仍是"终点 − 起点"**。而人的"挥一下"常常是**来回摆**（挥出去再收回来）→ 终点≈起点
→ `ΔX≈0`；这时只要纵向有累积（手臂摆动 + 掩码最高行被 ROI 重裁 + 镜头俯角让手斜着走），
`ΔY` 就独占，判据 `ΔY>120 且 |ΔX|<25` 成立 → **蓝条**。所以第 2 轮并没有真正堵住这条路。

**本轮改法：全部改用"整段峰值"**（偏离起点的最大幅度，而不是终点）：

- `S_gaxm` = 整段 max|x(t) − x0|、`S_gxpk` = 峰值时刻带符号的横向位移（定左右）、
  `S_gaym` = 整段 max|y(t) − y0|、`S_gdym` = 整段 **向下** max(y(t) − y0)。
- 判据：左/右 = `S_gaxm > 60 且 S_gaxm > 2·S_gaym`；下劈 = `S_gdym > 120 且 **S_gaxm** < 40`。
  **关键**：左挥的横向峰值是几百像素，`S_gaxm < 40` **结构上不可能成立** ——
  横挥误报下劈从"门限调参"变成"判据互斥"。
- `GEST_Y_XMAX` 25 → **40**（给"稍微斜一点的劈"留点余量）。
- DBG 的 `P` 字段改成**上一段的峰值幅度**（横向、向下），一直保留到下一段开始 ——
  挥完再读日志就能看到"这一挥到底走了多少像素"，用来定门限（不用盯实时值）。

**提示条改成"画在对应屏幕边缘"**（用户觉得固定位置换颜色不直观）：
左挥 = **左边**竖条、右挥 = **右边**竖条、下劈 = **底部**横条、方向不明确 = **顶部**细横条

### 2026-10-11（续 5）　M2.2 第 1 轮：指尖 + 手型（张开 / 握拳）—— 用逐行"峰数"，0 ERAM

**规划 vs 本实现**：规划里 M2.2 要"每列轮廓记忆（1280 列 / 或 320 列 ×10bit ≈ 1 块 ERAM）+
对轮廓序列找局部极大值"。本轮用一条**等价但省得多**的路子，**不用任何 ERAM**：

| 交付物 | 规划做法 | 本实现（省额度） |
| --- | --- | --- |
| 指尖坐标 | 轮廓最高峰的列 + 该列顶部 y | **顶带里遇到的第一个掩码像素**（自顶向下、行内左→右扫）→ 锁存列/行 |
| 手型（张开/握拳） | 对轮廓高度序列数局部极大值个数（≥2 峰 = 张开） | **逐行数"进入掩码的连续段数"**，取整帧最大：1 段 = 并指/握拳、≥2 段 = 手指分开 |
| 防抖 | 连续 N 帧一致才改状态 | 同（`M2_LOCK_FRAMES`=4 帧滞回） |

**为什么逐行数段数等价于数峰**：张开手在"指尖附近的那些行"上会被手指之间的缝切成 ≥2 段；
握拳/并指在这些行上是整块 → 1 段。所以"各行段数的最大值"就是规划的"轮廓峰数"，
而它**只需要 1 个标志位 + 4 位计数器 + 逐像素边沿检测**，不需要存任何轮廓。

**实现要点（都在 `recog_top.v` 的 `g_track` 里）**：

- **顶带** = 以"上一帧掩码最高行 `S_ymin`"为基准，向上 `M2_TOP_UP`=16、向下 `M2_TOP_DN`=48 像素。
  `S_ymin` 是 mask_stats 现成的帧锁存输出，手一帧走不了几十像素，这个带一定盖住当前手顶。
- **逐像素流水**（复用 M1 已有的 ROI 门控掩码 `S_mask_gated` + 每拍 4 像素 + 行号 `S_y_pos`）：
  数"由不在顶带 → 在顶带"的上升边 = 段数；**换行那一拍把上一拍最右像素作废**，免得上一行右端
  和新行左端连成一段（`S_m2_prev_eff`）。
- **帧首锁存**：`h_m2_tx/ty`（上一帧指尖）+ `h_m2_max`（上一帧最大段数）。叠加里画点用
  `h_m2_*`，所以**帧内稳定不抖**；手型状态机用刚结束那一帧的整帧结果。
- **可视化**：在指尖画一个 `(2·M2_TIP_R+1)²` 的方点（`M2_TIP_R`=3 → 7×7），
  **颜色 = 手型：黄 = 张开、红 = 握拳**；手型未知就不画。点画在所有视图之上（在 F_ovl_view 里
  优先级最高，连准星都盖不住它）。因为这一版 `isp_top` 的 `MASK_PREVIEW` 也置 1，
  **开机就能看到"掩码 + 准星 + 指尖点"，不用按 KEY4、不用串口**。
- **调试口径**：`M2_DBG=1` 把 DBG 的 **P/Q 借给 M2.2**（`R` 保持 M1 的包围盒 y，用来盯掩码健康）：

### 2026-10-11（续 6）　**肤色判据改"按亮度归一化"**（用户提议的治本修法）

**① 的根因**：老肤色判据是**绝对值窗**——`d2 = R−Y ≥ 3`、`|d1| = Y−B ∈ [5, 100]`。
光照一暗，R/B/Y 一起变小、**差值按比例缩小**，于是这个固定的下界（|d1| ≥ 5）先失效 →
手掉出窗口、掩码在暗处断开。**换门限治不了，必须换成比例判据**（用户说对了）。

**改法（本轮）**：新增判据 v3 `F_skin_norm_px`，用**比例**代替绝对值窗：

    d2/Y ∈ [2^-NORM_LO_SH, 2^-NORM_HI_SH]、|d1|/Y 同区间（默认 1/32 ~ 1/2）

实现**不用乘除**：边界直接把 Y 右移得到（`Y>>5` = Y/32、`Y>>1` = Y/2），下界再取 `max(1,·)`

老判据会被综合裁掉）。

### 第一次上板反馈与修复（2026-09-26 晚）

上板现象：**水果斜着直线飞、还没走到画面边缘就凭空消失**。查出四个原因，全部修掉：

1. **判定圆心错位（真 bug）**：`game_fruit` 原来直接拿对象**左上角**当圆心，比 64×64 精灵的

   改成 `中心 = 左上角 + 32`（乘法器操作数/累加器同步加宽到 14/28 位），并要求
   **中心在屏内（x ≤ 1279、y ≤ 719）才允许判定**。
2. **"走不到边缘就消失"（真 bug）**：漏切判定原来一过 `field_y1 = 704` 就把槽位清掉，而屏幕
   底边是 720 —— 水果**还剩 16 px 在屏内就没了**。改成：扣命仍然在 `field_y1`（每颗只扣一次，
   新增 `S_missed[6]`），但**槽位要等整颗掉出屏幕（中心 > 751）才回收**，水果能一路看着落下去。
3. **命数归零会清场**：原来 `state=2` 把所有水果一起删掉（像"突然全部消失"）。现在只停止生成，
   空中的果子继续飞完；并且**KEY4 打开游戏层的那一帧自动重开本局**（B 段还没接通、0x81 写不进来，

4. **"斜线运动"是手感参数问题**：水平初速原来 ±(0..7) px/帧，上升 48 帧就会横移最多 336 px
   （≈45°），抛物线被拉成对角线。改成 **±1~4 px/帧**，弧线就看得出来。

## 2026-10-16（续 4）　**从新实现运动门**：采样行轮转 + 像素级判决 + quiet 门 + 同源融合

用户给的**三条前提**（先定死，再写码）与**四步落地**，本轮全部落地（`recog_top.v` +
`isp_top.v` 各一处叠加使能）。签入后的行为：**档 2 = 运动门开 / 档 3 = 关（对照）**，
一版 bit 现场 A/B。

### 1. 三条前提（照做，不做变通）

| 前提 | 落地方式 |
|------|----------|
| ① 语义 = **背景帧差分**（不是帧间差分） | 删掉 `FRAME_DIFF`/`LATCH_MODE` 那条"背景 = 上一帧"的路（帧差会让静止的手 0.3 s 被吸进背景，与规格 §3"静止的手也检出"冲突） |
| ② 粒度 = **像素 vs 块参考值**（不是块 vs 块） | 判决改回逐像素 `|gray − bg|`；块级信息只剩"背景更新许可"（块内活动像素数） |
| ③ 开关 = **运行时档位** | 新增 `recog_algo == 2`（开）/ `== 3`（关，对照）；`isp_top` 把 2/3 也并进叠加使能，切档就能看画面 |

### 2. 四步落地

**Step A（块参考值）—— 采样行轮转 + 整行 16 像素 + 带系数的蠕变**

- 采样行 = `frame_cnt[3:0]`（本帧采"块内第 N 行"），16 帧覆盖整块 16 行 →
  **采样密度 6.25% → 100%**；写入天然被摊到 16 帧里，所以**旧的"按块地址低位挑帧"整段删掉**。
  ⚠ 顺手挖出一个真 bug：旧 `S_turn_sel = {2'b0, frame_cnt[3:0]}` 只有 6 位里的低 4 位在比、
  而 `S_addr_cur[5:0]` 是 0..63 ⇒ **地址低 6 位 ≥16 的块（占 3/4）永远拿不到更新机会**。
- 一行 16 像素 = 块内 4 拍：12 位累加器跨 4 拍，`phase==3` 取 `>>4` = 行均值。
- 更新律换成 `bg += clamp(|row_mean − bg| >>> BG_K, 1..BG_STEP_MAX)`（`BG_K=3` → 时间常数
  ≈2.1 s @60 fps）。**钳到 ≥1 必须保留**：纯移位在 |d| < 8 时截成 0，小残差永远修不回来。
- ERAM 时序随之改：`phase 2` 写**上一块**（地址 `S_addr_prev`）、`phase 3` 预取读下一块 ——
  因为新判决要等整行累加完（phase 3）才能定背景值，而 phase 3 是预取槽。读/写各占各的槽，
  3 拍延迟用"一对寄存器 + 消费后清零"实现（`S_pend_we/S_pend_data`）。
- 成本：≈+60 LUT6 / +12 FF；ERAM **+2 块**（背景帧那 2 块回来了）。0 DSP。

**Step B（判决）—— 逐像素，块级退位**

- 运动掩码 = 每像素 `|gray − bg| > MOTION_TH` **且** `(|d|<<3) > bg`（相对门保留）。
- **删掉 `{4{S_lat_on}}` 块级锁存判决 + 它的 1 块 ERAM 锁存表**：一个 16×16 块里几像素在动
  就整块 256 像素算"动过"，正是"挥一下出三条不同颜色的条 / 往左挥报下劈"的根源。

**Step C（quiet 门）—— 改成"块内活动像素数"**

- 允许蠕变的两种情形：① `活动像素数 ≤ BG_QUIET_PX(1)`（整块安静）；
  ② `活动像素数 == 16` 且 `|整块均值偏差| ≤ BG_UNIF_MAX(40)`（16 像素**齐步同向**变 =
  均匀光照漂移，否则灯一变亮区残差永远修不回来 —— 旧 quiet 单向棘轮的坑）。
- 其余（手在块里，只有一部分像素在动）→ **冻结** ⇒ **静止的手不会被吸进背景**，
  这就是"手停住不掉掩码"的机制（不靠锁存）。
- **手动采样入口**：切到档 2 的那一拍自动重建背景（32 帧自举）——
  现场"**手拿开 → `W 08 0002`**"就等于重新采一遍背景，不用重开机、不用按键
  （`TEACH_EN=0` 之后 KEY4 已无示教入口；长按 KEY4 的 `teach_cnt` 变化仍会重建背景）。

**Step D（融合）—— 掩码与软权重同源**

- `F_w_rgb` 的运动分改成与掩码**同一份**逐像素判据（同一 `S_bg_cur`、同一对门限）。
  历史上"桌面不涂红、准星却被拖走"就是两条路判据不同造成的，这条不变量写进注释了。
- 运动门关（非 2 档 / 背景未建好）时，权重与掩码都退回"只看肤色" ⇒ **档 0/1 交付行为一字不变**。

### 3. ① 块级占比门（用户指令）—— 落地为 **1 块 ERAM**

| 项 | 做法 |
|----|------|
| 块格 | **32×32**（40×23 = 920 块）→ **1 块 1024×8 ERAM**（用户给的"1 块 ERAM"预算） |

## 2026-10-17　**把画面弄亮**：数字增益改运行时可切 + 绝对常数按 ×2 重定

**用户决定**：不再调算法，先"把画面弄亮"（`DIG_GAIN_SHIFT` ×2 或 ×4），比例判据不动、
绝对常数重定一次。

### 1. 先修了一个**真 bug**（不然提亮只提亮屏幕）

`isp_top` 里两处注释互相矛盾，代码是后者：`S_awb_g`（带增益）**只喂显示**，
而 `recog_top` 的 `I_raw_tdata` 接的是**未增益**的 `awb_O_tdata`。
⇒ 以前把 `DIG_GAIN_SHIFT` 打开，只会让屏幕变亮、判据仍然吃暗流。
现在 **tap 也接 `S_awb_g`**：屏幕上看到的亮度 = 判据吃的亮度（灰阶视图 12 因此也与判据同源）。

### 2. 增益改成**运行时可切**（一版 bit 现场 A/B）

| 档 `W 08 000N` | 数字增益 |
|----------------|----------|
| 0/1/2/3/4/5/6/7/10/11 | ×1（交付档不变） |
| **8** / **12** / **13** / **14** / **15** | **×2** |
| **9** | **×4**（亮部会削顶；它原有的"柔和跟随"保留，看掩码不受影响） |

`DIG_GAIN_SHIFT` 非 0 时**强制覆盖**（1=×2、2=×4），方便以后一次编译定死。
切换是即时的：`W 08 0001`（×1）↔ `W 08 0008`（×2）↔ `W 08 0009`（×4）。

### 3. 绝对常数按 ×2 重定（比例项不动）

| 常数 | ×1 时 | ×2 后 | 理由 |
|------|-------|-------|------|
| `SKIN_Y_MIN` | 16 | **32** | 噪声底也翻倍，门槛跟着翻 |
| `SKIN_Y_CAP` | 200 | 200 | 皮肤在高增益下仍 ≤200；反光撞 255 被顶掉 |
| `SKIN_SAT_MIN` | 8 | **12** | ×2 下 ≈ 原来的 6（偏松一档先保手；手还被切就调 8） |
| `SAT` 比例 `Y/8` | — | 不变 | 比例判据本来就与亮度无关 |
| `OBS_Y_T1..T3` | 32/64/128 | **64/128/192** | 手（×1 时 32..63）现在落在 64..126 = 青档 |

### 4. 时序：增益插进了最紧的那条路，**必须打一拍**

第一版（不打拍）final Setup WNS 只剩 **+33 ps**（门禁要 ≥+300 ps），
最紧路径正是 `awb → 肤色判据 → g_cent 的 Σw·x 累加器` —— 运行时可切的增益

修法：增益后**整包打一拍**（`tdata + tvalid + tlast + tuser` 共 99 FF），
显示与识别支路仍严格同拍 ⇒ 叠加不错位，而长路被切成两段。

## 2026-10-18　**块级运动门修正：背景统一块均值 + 自愈**

## 2026-10-18　**块均值累加修正 + 块列索引修正**

### 上板现象（`M2_P1_MOTION_20261018`）

1. 静止手 10 秒：整只手连续、无块级闪烁、无横条缺口；手掌/指缝小洞被补上。
2. 慢移/快移：掩码整体跟手，允许 1～2 帧滞后；不应只在旧位置残留。
3. 空场档 1：不应出现红块；档 5（原始肤色）仍可看到背景候选，作对照。
4. 手入画：约 5～6 帧内锁定并出现整手掩码；手出画：随解锁消失。
5. 准星仍跟质心（手心），游戏刀尖仍走指尖。

## 2026-10-21　识别锁定振荡修复 + 行带隔离（两次构建）

### 现象与根因

- 上板：手静止约 1 s 后肤色掩码消失，黄十字/游戏刀锋乱跳，约 1 s 后掩码又出现；

  权重却仍乘运动分。手一停 `Σw` 归零 → 质心有效性与命中判据同时失效 → 5 帧后丢锁 →

- 构建：slices **17838（84.08%）**、LUT6 15871、ERAM 76/108、DSP 8/40、feedthrough 6772、
